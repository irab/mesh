Overview

Meshtastic

Meshtastic is an established open-source LoRa mesh networking project focused on creating a decentralized communication platform that works without relying on internet or cellular infrastructure. It enables text messaging, location sharing, and telemetry over mesh networks.

Official Website

MeshCore

MeshCore is a lightweight, portable C++ library and firmware suite for multi-hop packet routing over LoRa and other packet radios. It separates silent client companions from dedicated infrastructure repeaters and room servers, combining flood discovery with path-specific direct routing.

Key Differences

Routing Architecture

+

Meshtastic

Broadcasts use managed flooding. A client waits a contention window scaled by the received SNR, so a farther node tends to relay first, and cancels that relay if it hears another copy. ROUTER nodes relay in an earlier window and do not cancel. A direct message with a learned next hop is relayed only by that hop. This was already the live path in the v2.6.4 snapshot, via NextHopRouter, not an every-node rebroadcast.

MeshCore

Repeaters forward flood packets (with region scoping and hop-count priority decay) and path-specific direct packets (where only the matching next-hop repeater forwards, or zero-hop local direct when path_len = 0). Companion devices do not repeat.

Packet Forwarding

+

Meshtastic

A new packet with hop limit left is scheduled for one rebroadcast. The wait is short after a weak SNR and long after a strong SNR, and clients start only after the router window. If a client hears another node rebroadcast that packet first, it cancels. Hop limit 0 is not rebroadcast. Routers do not cancel.

MeshCore

Companion nodes never repeat. Dedicated repeaters forward DIRECT packets only when their hash is next in the path header, while FLOOD packets (discovery, adverts, group channels) are forwarded once per repeater within hop and region limits.

Network Structure

+

Meshtastic

Combines shared-key encrypted channels with X25519 public-key encrypted Direct Messages (v2.5+). Nodes sharing the same LoRa modem preset and frequency slot participate in managed flooding unless restricted by CLIENT_MUTE or rebroadcast_mode (LOCAL_ONLY / KNOWN_ONLY).

MeshCore

Combines explicit repeater-hash routes for public-key DMs with flooded shared-key group channels, plus Room Servers that act as store-and-forward BBS hubs for asynchronous messaging.

Congestion Management

+

Meshtastic

Managed flooding drops redundant client relays. Hop limit and duplicate detection bound the rest. Router and tracker roles are not scaled back the way ordinary clients are as the node list grows.

MeshCore

Employs a token-bucket airtime budget (50% default duty cycle in v1.18 via airtime_factor = 1.0, configurable; 33.3% in v1.6), combined with priority-based scheduling and airtime-scaled flood jitter.

Client Architecture

+

Meshtastic

Uses a unified firmware approach across different hardware platforms.

MeshCore

Provides separate role-specific firmware builds:

  1. Companion Radio (BLE, USB Serial, or Wi-Fi — client endpoints, never repeat)
  2. Repeater (dedicated forwarding backbone)
  3. Room Server (persistent BBS / message store)
  4. Sensor & KISS Modem builds

Disaster Scenario Performance

In a large-scale disaster scenario with many users (tens of thousands) across a wide area (hundreds of km²):

Meshtastic Strengths

  • Immediate message propagation without requiring path establishment
  • Higher probability of message delivery through redundant paths
  • Better for the initial emergency phase when reliable communication is critical

Meshtastic Challenges

  • Many simultaneous channel broadcasts can still saturate airtime — managed flooding cancels redundant client relays, but every broadcast wave still spans the mesh
  • Misconfigured ground-level ROUTER nodes or chatty telemetry defaults can degrade channel capacity
  • Default hop limit is 3 (max 7), trading extreme hop count for bounded channel utilization

MeshCore Strengths

  • More efficient bandwidth usage through selective routing
  • Priority system helps ensure critical messages get through
  • Room servers provide persistent messaging points for affected communities
  • Better performance over sustained usage periods

MeshCore Challenges

  • Initial path discovery requires time to establish efficient routes
  • Less redundancy could result in some message delivery failures
  • Requires more strategic node placement for optimal performance

Use Case Suitability

Meshtastic is better for:

  • Users wanting a fully open-source solution
  • Larger mesh networks with many nodes
  • Users who want an established platform with extensive documentation
  • Applications requiring extensive telemetry and sensor integration
  • Scenarios requiring immediate message propagation without path establishment
  • Emergency situations where message redundancy is more important than network efficiency

MeshCore is better for:

  • Custom embedded C++ projects needing a lightweight routing library
  • Planned networks with dedicated hilltop repeaters and silent handheld companions
  • Communities using Room Servers for asynchronous BBS-style message storage
  • Dense urban deployments where explicit multi-hop direct paths and region flood caps keep airtime low
  • Long-term fixed-infrastructure meshes prioritizing sustained unicast throughput

Conclusion

Both Meshtastic and MeshCore provide off-grid mesh communication using LoRa, with different routing. Meshtastic broadcasts use managed flooding: clients cancel a relay when another node has already transmitted that packet, and a learned direct-message next hop does not flood. MeshCore repeaters forward a flood once, then carry later traffic as direct packets along a path. Room servers add persistent storage.

For disaster scenarios, Meshtastic may perform better in the immediate aftermath when redundancy is critical, while MeshCore could provide more sustainable communication over time as the network stabilizes. The ideal solution might combine elements of both approaches or deploy them in complementary roles based on the specific requirements of the deployment area and expected user density.
