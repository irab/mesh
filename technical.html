What changed since the snapshot

Meshtastic v2.6.4 to develop

Managed flooding was already in v2.6.4. RadioInterface::getTxDelayMsecWeighted still maps SNR -20..10 onto contention windows 3..8, and clients still cancel when they hear another LoRa copy. The simulator models this along with LONG_FAST packet airtime (~560 ms, 28 ms slot time), Listen-Before-Talk CAD backoff, and 6 dB LoRa capture (matching Meshtasticator).

  • Still true: broadcasts, and direct messages with no next hop, are managed floods. A known next hop is relayed only by that node (NextHopRouter). Default hop limit is 3 (HOP_RELIABLE). Maximum is 7.
  • v2.6.4 treated REPEATER like ROUTER (early window, no cancel). Current firmware keeps the early window for ROUTER only. ROUTER_LATE still never cancels, and is clamped to the late window via clampToLateRebroadcastWindow.
  • CLIENT_BASE now refuses to cancel packets to or from a favorited node, and those relays use the late window.
  • Only LoRa duplicates cancel a relay. An MQTT copy does not (p->transport_mechanism == TRANSPORT_LORA).
  • Hop upgrade: a later copy with a strictly higher hop limit replaces a pending relay instead of cancelling it.
  • Favorite routers (Router::shouldDecrementHopLimit in v2.7+) preserve hop_limit on subsequent hops between favorited ROUTER/ROUTER_LATE/CLIENT_BASE nodes (the first hop hops_away == 0 always decrements). Develop (2.8) also adds HopScalingModule adaptive hop limits and gates hop-upgraded packets on a routing-auth check.
  • getCWsize signedness fix: v2.6.4 declared const uint32_t SNR_MIN = -20; later firmware fixed this to int32_t so 64-bit targets (portduino/native sim) do not wrap negative bounds.

MeshCore v1.6.0 to v1.18.0

Direct packets are still forwarded only by the next path hash. Flood packets are still forwarded once by repeaters, not cancelled when another repeater is heard. Repeater rx_delay_base is still 0 by default, so the SNR score delay is off unless an operator sets it.

  • Transport flood and regions. v1.18 repeaters can drop a flood whose transport code matches no allowed region. Unscoped floods are a separate case.
  • Separate hop limits for scoped flood, unscoped flood, and adverts (flood_max, flood_max_unscoped, flood_max_advert). v1.6 had a single flood_max.
  • Loop detection can refuse a flood that has already circled (minimal, moderate, or strict).
  • Multipart payloads and variable path-hash size were added. Companion radios still do not act as the repeater.
  • There is not a more popular replacement of this firmware. ripplebiz/MeshCore was renamed to meshcore-dev/MeshCore; it is the same repository. MeshOS, published for standalone T-Deck-class devices and associated with meshcore.co.uk, is a separate line that speaks the same radio protocol. Its public release repository is far smaller than meshcore-dev/MeshCore.

Core Routing Approaches

Meshtastic Routing Architecture

The active router in v2.6.4 was already NextHopRouter, not a naive flood. The old excerpt on this page was an earlier FloodingRouter::perhapsRebroadcast that the firmware was no longer using as the relay decision.

  1. Managed flood for broadcasts, and for direct messages that do not yet have a next hop.
  2. Next hop for a direct message whose next hop is known: only the addressed node relays it.
  3. Reliable retransmission of packets that still want an acknowledgement.

Managed flooding

When a node receives a packet it has not seen:

  1. It relays only if the hop limit is above zero, it is not the sender or the addressed node, and its role is allowed to rebroadcast. CLIENT_MUTE does not relay.
  2. It decrements the hop limit and waits before transmitting. SNR from -20 to +10 maps to a contention window of 3 to 8. A low SNR (far from the sender) draws a short delay. A high SNR waits longer. ROUTER transmits in the early window, random(0, 2 × CW) slots. Everyone else waits out 2 × CWmax slots first, then draws random(0, 2^CW).
  3. If a CLIENT hears another LoRa copy of that packet before its timer, it cancels. ROUTER and ROUTER_LATE do not cancel. ROUTER_LATE is held in the late window.

One transmission is heard by every neighbor in range. Counting a packet per neighbor, or relaying from every node that heard it, is not what the firmware does.

Packet Retransmission Logic

Reliable packets are queued until they are acknowledged or the retry count runs out:

  • In v2.6.4 and v2.7.26, NUM_INTERMEDIATE_RETX is 2. On develop (2.8) it is 3. The queued count is one less than that constant, because the first send already happened.
  • The original sender's NUM_RELIABLE_RETX is still 3.
  • Hearing the packet again stops a pending retry, except where the node was the explicit next hop.

Congestion Control & Packet Priority

Meshtastic scales periodic intervals based on node count and orders its TX queue by MeshPacket.priority:

  • TX queue priorities rank ACKs (120), alerts (110), and reliable DMs (70) ahead of default messages (64) and background telemetry/position (10)
  • ROUTER nodes don't have periodic intervals scaled; SENSOR/TRACKER roles keep priority for telemetry and position
  • Regular CLIENT nodes scale back periodic broadcasts as the network grows
Congestion Scaling 
uint32_t Default::getConfiguredOrDefaultMsScaled(uint32_t configured, uint32_t defaultValue, uint32_t numOnlineNodes)
{
    // If we are a router, we don't scale the value. It's already significantly higher.
    if (config.device.role == meshtastic_Config_DeviceConfig_Role_ROUTER)
        return getConfiguredOrDefaultMs(configured, defaultValue);

    // Additionally if we're a tracker or sensor, we want priority to send position and telemetry
    if (IS_ONE_OF(config.device.role, meshtastic_Config_DeviceConfig_Role_SENSOR, meshtastic_Config_DeviceConfig_Role_TRACKER))
        return getConfiguredOrDefaultMs(configured, defaultValue);

    return getConfiguredOrDefaultMs(configured, defaultValue) * congestionScalingCoefficient(numOnlineNodes);
}

MeshCore Routing Architecture

MeshCore wire headers encode four route types (FLOOD, DIRECT, plus region-scoped TRANSPORT_FLOOD and TRANSPORT_DIRECT in v1.18). Companion radios originate and receive; only dedicated repeaters forward:

  1. Flood Routing (FLOOD / TRANSPORT_FLOOD): Repeaters append their path hash (1–3 bytes) and retransmit once with priority- and distance-based scheduling
  2. Direct Routing (DIRECT / TRANSPORT_DIRECT): Path-specific forwarding where only the next matching repeater pops its hash and relays
  3. Zero-Hop Helper (sendZeroHop): Sends ROUTE_TYPE_DIRECT with path_len = 0 for local single-hop neighbors

Selective Packet Forwarding

MeshCore repeaters only forward direct packets when they match the head of the path:

  • Only forwards direct-routed packets if this repeater's hash matches the next entry in pkt->path
  • Checks the seen-packet ring buffer (wasSeen / markSeen) before forwarding
  • Removes its own 1–3 byte hash via removeSelfFromPath(pkt) so the frame shrinks at every hop
Packet Routing Logic (v1.18) 
if (pkt->isRouteDirect() && pkt->getPathHashCount() > 0) {
  if (self_id.isHashMatch(pkt->path, pkt->getPathHashSize()) && allowPacketForward(pkt)) {
    uint32_t d = getDirectRetransmitDelay(pkt);
    if (!_tables->wasSeen(pkt)) {
      _tables->markSeen(pkt);
      removeSelfFromPath(pkt);
      return ACTION_RETRANSMIT_DELAYED(0, d);  // Routed traffic is HIGHEST priority
    }
  }
  return ACTION_RELEASE;  // Not next hop (or already forwarded), discard
}

Priority-Based Transmission

MeshCore schedules outbound packets by priority (lower number = higher priority):

  • Direct-routed packets get highest priority (0), and flooded relays degrade priority as hop count grows (packet->getPathHashCount())
  • Originated flood data messages start at priority 1
  • Path return / discovery packets start at priority 2
  • Advertisements start at lowest priority (3)
Flood Routing with Priority (v1.18) 
void Mesh::sendFlood(Packet* packet, uint32_t delay_millis, uint8_t path_hash_size) {
  packet->header &= ~PH_ROUTE_MASK;
  packet->header |= ROUTE_TYPE_FLOOD;
  packet->setPathHashSizeAndCount(path_hash_size, 0);

  _tables->markSeen(packet);

  uint8_t pri;
  if (packet->getPayloadType() == PAYLOAD_TYPE_PATH) {
    pri = 2;
  } else if (packet->getPayloadType() == PAYLOAD_TYPE_ADVERT) {
    pri = 3;   // de-prioritise adverts
  } else {
    pri = 1;
  }
  sendPacket(packet, pri, delay_millis);
}

Congestion Mitigation

MeshCore employs several congestion mitigation techniques:

  • Token-Bucket Airtime Budget: Uses duty_cycle = 1 / (1 + factor). v1.6 defaulted to factor 2.0 (~33.3% airtime); v1.18 defaults to factor 1.0 (50% airtime, configurable via airtime_factor)
  • Airtime-Scaled Flood Jitter: Spreads simultaneous repeater retransmissions across 0..5 × (airtime / 2)
  • Hop-Count Priority Decay: Flooded packets lose priority with each hop (pri = getPathHashCount())

Network Capacity Analysis for Large-Scale Disasters

This analysis examines how each platform would perform in a large-scale disaster scenario with approximately 50,000 people trying to communicate across a mesh of 1,000 nodes in 300 km².

Meshtastic Network Capacity

Broadcast Storm Risk

A channel with tens of thousands of people sending at once can still congest. That is not because every node retransmits every packet:

  • Each client schedules one relay, then cancels it if another node transmits that packet first. Routers do transmit
  • Congestion scaling slows ordinary clients as the node list grows. It does not create extra airtime

Resource Utilization

  • Under heavy load, lower-priority or oldest queued packets are dropped first

Congestion Control

  • Meshtastic implements hop limits (default 3, max 7; adaptive via HopScalingModule on 2.8 develop)
  • MeshPacket.priority orders ACKs and alerts ahead of standard text and background telemetry
  • Client relays are cancelled once another copy is heard. Routers keep theirs, by design

MeshCore Network Capacity

Selective Forwarding

Seen Packet Tracking (v1.18) 
bool wasSeen(const mesh::Packet* packet) override {
  uint8_t hash[MAX_HASH_SIZE];
  packet->calculatePacketHash(hash);

  const uint8_t* sp = _hashes;
  for (int i = 0; i < MAX_PACKET_HASHES; i++, sp += MAX_HASH_SIZE) {
    if (memcmp(hash, sp, MAX_HASH_SIZE) == 0) {
      if (packet->isRouteDirect()) _direct_dups++;
      else _flood_dups++;
      return true;
    }
  }
  return false;
}

Direct packets are forwarded only by the next hop on the path. Flood packets are still forwarded by each repeater that has not hit the flood hop limit, region filter, or loop check:

  • Significantly reduces network-wide traffic compared to flooding
  • Well-suited for dense node deployments

Prioritization System

  • Assigns highest priority to direct messages (pri = 0) over flood messages (pri = 1..3)
  • Assigns decreasing priority as flood packets propagate further from source (pri = getPathHashCount())

Airtime Management

  • Token-bucket airtime budget caps sustained duty cycle (50% default in v1.18 via airtime_factor = 1.0; 33.3% in v1.6)
  • Implements airtime-scaled randomized retransmission delays and CAD retry backoff

Performance Predictions for 300km² with 1K Nodes

Meshtastic Performance

Message Propagation

  • With configured hop limits, messages would reach approximately 7-10km radius
  • Nodes would need to be positioned within 1-2km of each other for reliable coverage
  • Would require strategic node placement for full coverage

Broadcast Efficiency

  • High redundancy ensures messages reach destinations if any path exists
  • At 50K users sending messages, network would likely experience significant congestion
  • Congestion scaling would increase intervals between broadcast messages

Scalability Concerns

  • Each new channel broadcast still triggers one managed-flood wave across the mesh
  • Hidden-terminal LoRa collisions rise sharply when many senders transmit concurrently on slow presets like LONG_FAST
  • Packet pool and TX queue slots fill quickly under sustained burst load

MeshCore Performance

Message Propagation

  • Direct routing requires established paths
  • Initial network formation would rely on announce packets
  • With 1K strategically placed nodes, path discovery may take time but would be more efficient

Traffic Management

  • Selective forwarding means significantly less network congestion
  • Room servers could act as regional message collection points
  • Airtime limiting prevents any single node from overwhelming the network

Scalability Strengths

  • Priority system gives preference to direct routed packets
  • Random delays prevent collision storms after regional events
  • Decreasing priority with distance prevents distant nodes from consuming bandwidth

Optimizations for Disaster Scenarios

Optimizing Meshtastic

  1. Restrict ROUTER to True High-Site Peaks: Over-deploying ROUTER increases collisions because routers transmit in the early window and never cancel duplicates; keep ground/handheld nodes on CLIENT or CLIENT_MUTE
  2. Hop limit & faster presets: The default hop limit is 3 (max 7); lowering hop depth or switching dense meshes to faster presets (e.g. MEDIUM_FAST / SHORT_FAST) cuts airtime per hop dramatically
  3. Throttle Background Broadcasts: Lengthen position, telemetry, and NodeInfo intervals so human text and alerts retain channel capacity
  4. Use Direct Messages Where Possible: Once NextHopRouter learns a next hop, DMs forward via a single relay per hop instead of flooding

Optimizing MeshCore

  1. Pre-established Room Servers & Transport Regions: Deploy room servers at key hubs and scope floods with v1.18 transport region codes
  2. Optimize Advert & Unscoped Flood Caps: Tune flood_max_advert and flood_max_unscoped in high-density areas
  3. 2- or 3-Byte Path Hashes in Large Meshes: Avoid single-byte repeater hash collisions across hundreds of repeaters
  4. Tune airtime_factor & rx_delay_base: Raise airtime_factor above 1.0 (tightening duty cycle below 50%) and enable SNR-based rx_delay_base on dense repeater clusters

Technical Conclusion

In a large-scale disaster scenario with 50,000 users across 1,000 nodes in 300 km²:

Meshtastic broadcasts with managed flooding, so a packet is not retransmitted by every node that hears it. A busy channel can still run out of airtime. Direct messages switch to a single next hop once that hop has been learned.

MeshCore would offer more sustainable communication over time through its selective routing and prioritization schemes. While initial path discovery might take longer, the network would maintain higher throughput once paths are established, especially with strategic room server placement.

For maximum resilience, a hybrid deployment could leverage Meshtastic's flooding for critical emergency messages and MeshCore's selective routing for sustained communication channels.
